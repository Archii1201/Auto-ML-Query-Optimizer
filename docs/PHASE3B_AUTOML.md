# Phase 3B — AutoML-Tuned Learned Cost Model

> Goal: take the Phase 3A pipeline from "interesting prototype" to a
> credible AutoML-driven cost model that *picks the optimal plan*,
> not just predicts a number.

This document explains every change made in Phase 3B, why it was
made, and how to reproduce the full pipeline end-to-end.

---

## 1. Mental model — what Phase 3B adds on top of 3A

Phase 3A taught us four uncomfortable truths:

1. **The dataset was tiny** — 87 plans, 22 distinct queries.
2. **The features were too thin** — only raw cost, no log-scale,
   no plan-shape ratios, nothing about historical cardinality
   error.
3. **The metrics didn't reflect deployment** — we never asked the
   model "which of these 4 variants is fastest?".
4. **Hyperparameters were arbitrary** — every model used out-of-the-
   box defaults from sklearn / XGBoost / LightGBM / CatBoost.

Phase 3B fixes all four:

| Phase 3A | Phase 3B |
| --- | --- |
| 87 plans, 22 queries | ~610 plans, ~130 queries (param TPC-H + TPC-DS) |
| 50 features, raw scale | 59 features, +log-cost, +plan-shape ratios |
| MAE / RMSE / R² / MAPE / q-err / Spearman ρ | …all of the above + **plan-pick accuracy** + **regret** |
| Sklearn / XGB / LGBM defaults | **Optuna** TPE search, 25 trials per tunable model |
| 1 model class, no winner picked | **AutoML model selector** chooses best model per regime |
| Plain `LinearRegression` (unstable) | Replaced with `Ridge` / `Lasso` / `ElasticNet` |

> **The "AutoML" headline.** Instead of "I trained nine models",
> Phase 3B says: "I trained twelve models (3 linear + 5 tree) under
> two regimes, ran 250+ Optuna trials, and the system itself picked
> the winner using a composite of median q-error and plan-pick
> accuracy."

## 4. Module deep-dive

### 4.1 `feature_engineering/extract_features.py` — additions

Nine new strictly-plan-time columns:

```text
# log1p of skewed cost / size signals
log1p_estimated_total_cost
log1p_estimated_startup_cost
log1p_estimated_rows
log1p_max_subtree_cost
log1p_total_nodes

# plan-shape ratios — invariant to absolute cost magnitude
cost_per_estimated_row     = total_cost / max(plan_rows, 1)
startup_to_total_ratio     = startup_cost / max(total_cost, 1)
max_to_root_cost_ratio     = max_subtree_cost / max(root_total_cost, 1)
est_rows_per_node          = plan_rows / max(total_nodes, 1)
```

Why log1p? Tree-based models are scale-invariant *across splits*,
but linear / GLM models cannot represent power-law fit unless you
hand-feed log scale. Cost values span 4-5 orders of magnitude;
without log1p, Ridge and Lasso are essentially memorising the few
big-cost queries and predicting their mean for everything else.

### 4.2 `db/tpch_param_queries.py` & `scripts/collect_tpch_param_plans.py`

The vanilla 22 TPC-H queries fix every parameter (e.g. Q1 always
filters on `l_shipdate <= '1998-12-01'`), giving a single plan
per query. Param TPC-H instead picks **5 parameter sets per
query** (sampling reasonable ranges from the spec), which
generates plans with very different cardinalities and hence
different optimal joins.

Schema-compatible with Phase 2A: same JSON record format, same
4-variant fan-out, same `_index.jsonl`. Output goes to
`data/tpch/plans_param/`.

### 4.3 `db/tpcds_queries.py` & `scripts/setup_tpcds.py` & `scripts/collect_tpcds_plans.py`

TPC-DS introduces a *very* different workload: 24 tables, much
heavier dimensional joins, window functions. We picked 20 queries
that:

- run cleanly on PG without dialect surgery,
- exercise the three fact tables (`store_sales`, `web_sales`,
  `catalog_sales`), and
- produce diverse plan shapes (joins / aggregates / windows /
  TOP-K / self-joins).

The schema is **auto-generated** from DuckDB's introspection so
we don't hand-maintain 24 CREATE TABLE statements:

```python
# scripts/setup_tpcds.py
con.execute("LOAD tpcds; CALL dsdgen(sf=0.1)")
schema_sql = _emit_schema_sql(con)   # introspect DuckDB → PG DDL
SCHEMA_FILE.write_text(schema_sql)
```

### 4.4 `phase3b/tuning.py` — Optuna search spaces

Five tree models are tunable:

| Model | Knobs (≈ search space size) |
| --- | --- |
| RandomForest | n_estimators, max_depth, min_samples_leaf, max_features |
| ExtraTrees   | same as RF |
| GradientBoosting | n_estimators, max_depth, lr, subsample |
| XGBoost      | n_estimators, max_depth, lr, subsample, colsample, reg_lambda |
| LightGBM     | n_estimators, num_leaves, max_depth, lr, subsample, colsample, reg_lambda, min_data_in_leaf |

**Objective:** `q_error_median` averaged across 5 GroupKFold folds.

Why q-error median, not RMSE?
- q-error is the standard metric in the learned cost model
  literature (Sun & Li 2019, Kipf et al. 2019, MSCN, NEO).
- It's symmetric: predicting `2x` and `0.5x` of truth both score 2.
- It's robust to one-shot outliers (a single 100ms→100s mistake
  doesn't blow up the *median* the way it does RMSE).

CatBoost is **not** tuned because (a) its default is competitive,
(b) its built-in Bayesian optimiser is faster than wrapping it in
Optuna, and (c) tuning all five tree models already gives the
AutoML selector enough candidates.

Linear models (Ridge / Lasso / ElasticNet) are also not tuned —
the gain from searching `alpha` is marginal vs. the time cost,
and they are never the AutoML winner anyway.

### 4.5 `phase3b/plan_pick.py` — the metric that actually matters

For each `query_id` group of 4 variants:

```python
true_best = argmin(actual_time)   # truth
pick      = argmin(predicted_time) # model's choice
hit       = int(true_best == pick)
regret_ms = actual_time[pick] - actual_time[true_best]
```

We report:
- **plan-pick accuracy** = mean(hit) — what fraction of queries
  does the model send to the correct variant?
- **regret_ms_mean** — average extra wallclock paid vs. the
  oracle.
- **regret_ratio_p95** — 95th-percentile of relative slowdown.

A great model can have a *terrible* RMSE but a *perfect* plan-pick
accuracy: it can be off by 200% in absolute prediction yet always
rank the variants in the right order. That's exactly what a
production query optimizer needs.

### 4.6 `phase3b/train_models.py` — the AutoML selector

```text
for regime in (plan_time, post_mortem):
    for baseline in (PG_linear, PG_loglinear):
        run_cv  → record metrics + preds
    for model in default_zoo:
        run_cv  → record metrics + preds + feature importance
    for model in TUNABLE:
        Optuna study (25 trials, 120s budget)
        run_cv with best_params  → record metrics + preds
        save tuned model artifact

# After all CV done, group preds by (model, regime) and compute
# plan-pick accuracy + regret per cell.

# Pick winner per regime:
score = q_error_median - 0.1 * plan_pick_accuracy
winner = argmin(score)  # over {default_ml, tuned_ml} only

# Persist the winner as automl_best.joblib for downstream loading.
```

The composite score balances "absolute prediction quality"
(q-err median) with "deployment quality" (plan-pick accuracy).
A model that's slightly worse at point prediction but better at
ranking variants wins — which is what we want.

## 6. Pitfalls & gotchas

1. **Statement timeout.** Some TPC-H queries (Q21 with no_mergejoin
   especially) can run >5 min. We set `statement_timeout = 5 min`
   in the collector — those rows are simply skipped, not zeroed.

2. **GroupKFold is mandatory.** Without it, the 4 variants of the
   same query end up split between train and test. The model
   memorises the query and `R² = 0.99`. We saw this in early
   3A runs.

3. **Optuna timeout vs. n_trials.** Whichever caps first wins.
   Default is `--n-trials 25 --tune-timeout 120`. For LightGBM
   this is more than enough; for RF on the largest regime you may
   want `--tune-timeout 300`.

4. **Plan-pick eval needs the `variant` column** in `cv_predictions.csv`.
   `train_models.py` keeps it intact via `variant_series`. If you
   add a new model that bypasses `run_cv()`, you must do the same.

5. **AutoML selector excludes baselines.** A calibrated PG cost
   model can be a great median predictor for tiny datasets, but
   we deliberately don't allow it to win — the whole point of
   Phase 3B is to ship an *ML* winner. Baselines remain on the
   leaderboard for comparison.

## 7. What this phase does NOT do (intentionally deferred)

| Feature | Phase | Reason |
| --- | --- | --- |
| LambdaRank ranking objective | future | The user's spec is "predict time → compare → pick min". Pointwise regression matches this; LambdaRank is a different (and IMHO weaker) framing. |
| Quantile regression / prediction intervals | Phase 4+ | Useful for safety nets ("don't pick a plan whose 95th-percentile latency is bad"), but blocks the deployment loop on its own. |
| Cardinality-error features from history | Phase 3C | Requires fold-aware aggregation (test row's feature must be computed only from train rows). Adds a layer of CV plumbing we don't need yet. |
| JOB workload (IMDB, ~3.5 GB) | future | The data is great but the download is huge and brittle. Param TPC-H + TPC-DS already gives 7× the Phase 3A volume with diverse plan shapes. |
| Online retraining loop | Phase 4 | Belongs in the system-design phase. |
